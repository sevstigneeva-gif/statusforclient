# Правила оценки проблем и рисков

Все риски рассчитываются независимо для каждого проекта. Каждая категория ниже должна быть подтверждена данными Jira.

## Категории

1. **🔴 Проблема** — due date или deadline уже нарушен, а задача остается незавершенной; либо задача явно заблокирована.
2. **🔴 Высокий риск** — remaining estimate больше доступного рабочего времени до соответствующего срока.
3. **🟡 Риск** — remaining estimate равен доступному рабочему времени до срока, поэтому временного запаса на последующие этапы нет. Последующие этапы учитывать, только если они явно зафиксированы в Jira; не придумывать их наличие.
4. **🟡 Явный риск** — риск явно зафиксирован в Jira: в описании, комментариях или другом поле для фиксации рисков.

Если выполняется несколько критериев одновременно — использовать наиболее высокий уровень.

## Правила формулирования

- Не создавать несколько рисков по одной и той же причине. Если одна причина влияет на несколько задач — один риск, в котором перечислены все значимые зависимые задачи. Не дублировать один риск отдельно для каждой задачи.
- Если риск влияет на несколько этапов или результатов — указать это в описании.
- Пример объединения: «🔴 Высокий риск: сроки предоставления данных заказчиком создают риск для реализации блока авторизации. От зависимости находятся WEB-123, WEB-127 и WEB-130».
- Не писать «задача точно не будет выполнена в срок». Писать «Есть высокий риск нарушения срока: estimate оставшихся работ — 3 рабочих дня, до срока остается 2 рабочих дня».

## Estimate и данные

- Если Jira дает remaining estimate — использовать его.
- Если доступен только первоначальный estimate всей задачи и остаток определить нельзя — не использовать его как точную оценку оставшейся работы.
- При достаточных данных учитывать: текущий статус, выполненную работу, оставшийся estimate, соответствующий срок, связанные задачи, последующие этапы (если явно зафиксированы).
- Estimate отсутствует → нельзя делать вывод о риске на основе предполагаемого объема работы. Срок отсутствует → нельзя делать вывод о риске по срокам. Нет ни estimate, ни срока → в риски могут попасть только явно заблокированные задачи, задачи с blocker/flag и задачи с явно зафиксированным в Jira риском.
- Сам статус In Progress риском не является.

## Рабочие дни

- Приоритет: рабочий календарь проекта, если доступен; иначе стандартный график понедельник–пятница. Официальные праздники исключать только при наличии доступного календаря. Календарь проекта не придумывать.
- Не использовать часы, если estimate задан в рабочих днях. Не рассчитывать неполные дни и часы без надежных данных.
- Считать скриптом (запускать по абсолютному пути из базовой папки скилла): `python3 <skill_dir>/scripts/working_days.py FROM TO [--holidays 2026-01-01,...] [--exclude-start] [--show-days]` — выводит число рабочих дней пн–пт в диапазоне включительно. День недели каждой даты вычисляется из реального календаря (закономерности по номеру дня в месяце нет: 20-е число в одном месяце может быть выходным, в другом — рабочим). `--exclude-start` не учитывает первый день (см. ниже); `--show-days` печатает построчную проверку каждой даты с днем недели и причиной пропуска — использовать для сверки с календарем. Праздники и перенесенные выходные передавать только из реального календаря через `--holidays` / `--holidays-file`.

### Доступное время до срока

Количество рабочих дней между датой анализа и соответствующим сроком. Если дата анализа — рабочий день и точное время неизвестно, не считать его автоматически полным оставшимся рабочим днем: используй `--exclude-start`.

Пример: анализ 2026-09-24 (чт), срок 2026-09-30 (ср). Рабочие дни 24–30 включительно — 5; без дня анализа — 4 (25, 28, 29, 30).

## Формализация риска по срокам

При наличии remaining estimate и соответствующего срока:

| Сравнение | Категория |
|---|---|
| remaining estimate > доступных рабочих дней | 🔴 Высокий риск |
| remaining estimate = доступным рабочим дням | 🟡 Риск |
| remaining estimate < доступных рабочих дней | риска по этому критерию нет |

- Если последующие этапы явно требуют времени, отсутствие запаса после текущей задачи — тоже риск.
- Несколько задач от одного ограничения → один риск с перечислением зависимых задач.
- Пример: «🟡 Риск: на разработку остается 2 рабочих дня, а до срока — 2 рабочих дня. Временного запаса на последующее тестирование нет. Зависимые задачи: WEB-123, WEB-125».
