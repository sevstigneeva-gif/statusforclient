# Формат статус-отчета

Отчет выдавать в чате как готовый к копированию текст. Отчет состоит из служебной информации (для РП и внутренней проверки, не для клиента) и клиентского статуса.

## Служебная информация

Формировать отдельно по каждому проекту:

```
Служебная информация
Период: [дата начала — дата окончания]
Проект: [название проекта]
Отбор задач: [все задачи по доскам проекта / только задачи с лейблами …, если заданы особенности отбора]
Проанализировано задач: [N]
Изменения за период: [N]
Завершено: [N]
Проблемы/риски: [N]
План на следующий период: [определён / определён частично / не зафиксирован в Jira]
```

Показатель, который невозможно достоверно определить, не придумывать. Завершено считать по проектному критерию завершенности из реестра проектных правил (project-rules.md), если для проекта он задан; иначе — по факту закрытия задачи.

## Структура клиентского статуса

Один проект — стандартная структура из пяти разделов:

```
Результаты за период
— [результат]
— [результат]

Проблемы и риски
🔴 [проблема / высокий риск + связанные задачи]
🟡 [риск / явный риск + связанные задачи]
или: Существенных проблем и рисков по данным Jira не выявлено.

Изменения по срокам
— [изменение срока]
(раздел выводить только при наличии значимых изменений)

Следующий период
— [планируемый результат]
— [планируемый результат]

Нужно от заказчика
— [конкретное действие + срок, если указан]
(раздел выводить только при наличии данных в Jira)
```

Несколько проектов — не объединять результаты в общий список, если теряется принадлежность к проекту. Для каждого проекта отдельный блок:

```
[Название проекта]
Результаты за период
— ...
Проблемы и риски
— ...
Изменения по срокам
— ...
Следующий период
— ...
Нужно от заказчика
— ...
```

Информация между проектами не смешивается.

## Результаты за период

Формулировка отвечает на вопрос: что произошло / что сделали → какой результат получили / на каком этапе сейчас находимся.

Глаголы: завершили, реализовали, запустили, передали на тестирование, согласовали, утвердили, исправили, подготовили, начали, продолжили, провели анализ/встречу, изучили, подготовили варианты. «Провели анализ» и «провели встречу» допустимы и значимы, если отражают реальную работу проекта. Примеры:

- Провели анализ текущего пользовательского пути и выявили основные точки для доработки.
- Провели встречу по требованиям и зафиксировали согласованный сценарий.
- Изучили текущую архитектуру интеграции и подготовили варианты решения.

Не включать действие только потому, что оно произошло, — оценивать значимость для проекта. Связанные задачи группировать (см. SKILL.md), технический шум исключать.

## Проблемы и риски

Раздел выводить всегда. Если проблем и рисков нет: «Существенных проблем и рисков по данным Jira не выявлено». Категории и правила расчета — в [risks.md](risks.md).

## Изменения по срокам

Показывать только при существенных изменениях. Учитывать отдельно друг от друга: изменение due date, изменение deadline, просрочку, приближение срока, перенос плановой даты, существенное изменение целевого срока. due date и deadline не смешивать; если изменены оба — показывать оба отдельно.

Не называть задачу просроченной, если соответствующий срок отсутствует. Не дублировать информацию, полностью раскрытую в «Проблемах и рисках». Нет значимых изменений — раздел не выводить.

## Следующий период

Включать:

- **To Do** — задачи, запланированные к началу или выполнению в следующем периоде.
- **In Progress** — только те, что планируется завершить, передать на следующий этап или получить по ним значимый результат, и есть дополнительное подтверждение: близкий срок, комментарий, описание, предыдущий отчет, явно зафиксированный следующий этап. Пример: «Завершить разработку личного кабинета (WEB-123) — задача уже в работе, завершение планируется в следующем периоде».

Не включать автоматически: все задачи In Progress, старые задачи без признаков движения, завершенные задачи.

Формулировать через ожидаемый результат: завершить, передать на тестирование, реализовать, подготовить, запустить, согласовать. Связанные задачи можно группировать. Если план зафиксирован частично: «План на следующий период в Jira зафиксирован частично». Если плана нет: «План на следующий период в Jira не зафиксирован». Самостоятельно отсутствующий план не реконструировать.

Отслеживать жизненный цикл задач через периоды. Пример: прошлый период «начали разработку каталога» → текущий «продолжили разработку каталога, реализовали основные сценарии» → следующий «завершить разработку каталога и передать на тестирование». План должен подтверждаться данными Jira или предыдущими отчетами того же проекта.

## Нужно от заказчика

Только явные действия, зафиксированные в Jira: согласование, предоставление материалов/доступа/данных, принятие решения, проверка результата, подтверждение требований. Если указан срок — указывать его.

Одно действие заказчика, влияющее на несколько задач, — один запрос со списком зависимых задач/результатов, а не запрос на каждую задачу. Действия не придумывать. Нет действий — раздел не выводить.

## Бюджет

Оценку бюджета на основании Jira estimate не формировать: не переводить story points, часы или дни в деньги, не делать выводов о перерасходе, не создавать финансовый статус без финансовых данных. Надежных финансовых данных нет — раздел «Бюджет» не создавать.

## Стиль

Краткий, деловой, конкретный, понятный заказчику без знания структуры Jira. Без лишней Jira-терминологии, канцелярита, субъективных оценок, искусственного позитивного тона и лишних вводных фраз. Активные формулировки: «Провели анализ текущего решения», а не «В рамках отчетного периода командой была проведена работа по...».

## Приоритет информации при анализе

Значимые результаты → существенные изменения продолжающихся задач → переходы между этапами → релизы и передачи → аналитика/обследования/дизайн → согласования и решения → проблемы и блокеры → риски → изменения сроков → план следующего периода → действия заказчика.
