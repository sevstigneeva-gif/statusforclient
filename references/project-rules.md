# Реестр проектных правил статус-отчетов

Индивидуальные правила по проектам: скоуп досок, отбор задач, критерий завершенности, период отчета, терминология, обращение к заказчику, календарь, прочие особенности выборки. Реестр ведется пользователями: чтобы задать или изменить правила проекта, допишите или поправьте его секцию ниже.

Правила одного проекта не действуют на другие проекты, даже если проекты похожи. Перед формированием отчета найти проект в реестре и применять только его правила. Проекта в реестре нет — работать по умолчанию из SKILL.md (все задачи по выбранному набору досок, завершенность = закрытие задачи) и уточнить у пользователя все вводные первого отчета (см. SKILL.md, входные данные).

Если пользователь в диалоге сообщает правила проекта («по этому проекту собирать только…», «завершено у нас — это…», «называйте так-то») — дописать их в реестр, чтобы следующие отчеты собрались правильно без повторных уточнений.

## Petstory (MARS)
- Скоуп досок: только разработка — доска Features (rapidView 717). Доски Requirements (725), Client (725), Manager (829) в отчет по разработке не входят.
- Трек требований в отчет по разработке не входит: задачи типов Проектирование, Дизайн, Продуктовая аналитика исключаются из всех выборок, даже если у них есть спринтовые лейблы. Исключение: задача, у которой на тикете висит флаг и в комментариях которой прямо написано, что она заблокирована задачей аналитики/дизайна и т.п., включается в отчет (в проблемы и риски) с указанием блокирующей задачи.
- Отбор задач: только задачи с лейблами Sprint_goal, Sprint_dev, Reserve — целевые задачи спринта, задачи цели-разработки, резервные задачи. Задача попадает в отчет, если у нее есть хотя бы один из этих трех лейблов (даже если вместе с ними стоят Focus или DT); задачи без спринтовых лейблов в отчет не входят.
- Период отчета: спринт — 2 недели. Если период не указан, запросить даты спринта (например, 07.09.2026–20.09.2026).
- Критерий завершенности: задача завершена, когда передана в prod-тестирование (статусы To prod release, In prod test). Статус Done как критерий завершенности не используется (Done = реализована, вылита на prod и протестирована).
- Обращение к заказчику: не «заказчик», а «Марс» — раздел «Нужно от Марса».
- Терминология:
  - A/B-тесты называть «Growth Hacking» (тип задач Growth Hacking, префикс GH в названии задачи); не «эксперименты».
  - Задачи разработки (типы Component, Fix, DevOps) не называть «проектированием». Проработку требований ведут отдельные типы задач — Дизайн, Продуктовая аналитика, Проектирование (доска Requirements); в отчете формулировать «проработали требования / подготовили ТЗ», «подготовили дизайн».
- Воркфлоу и статусы: полное описание типов задач и статусов — [references/petstory-workflow-jira.pdf]. Ключевое для отчета:
  - Component/Fix (разработка): Open → To Do → In Progress → In review → In Debug → To dev → In dev test → To stage release → In stage test → To prod release → In prod test → Done | Cancelled.
  - Дизайн / Продуктовая аналитика / Проектирование: Open → To Do → In Progress → In review → Client Acceptance → Done | Cancelled. Статус Client Acceptance — задача передана на ревью Марса. Задачи этого трека в отчет по разработке не входят (см. скоуп), поэтому их Client Acceptance сам по себе не создает пункт «Нужно от Марса».
  - Epic: Open → In requirements → Epic test → Requirements done → Epic in progress → Done | Cancelled.
  - Growth Hacking: статус To apply — гипотеза подтверждена и остается на постоянке. По регламенту Done у GH-задачи означает неподтвердившуюся гипотезу (чистка кода), но в проекте статус Done встречается и у раскатанных тестов — при неоднозначности опираться на комментарии задачи и не подавать Done автоматически ни как успех, ни как провал.
  - Блокировки: флаг Flagged = Impediment с причиной в задаче (также встречается статус Blocked); причину блокировки брать из комментариев/описания флага.
- Прочее: комментарии к задаче не приходят в issue_get — забирать через issue_comments_list.
