# Организация работы: статусная отчетность по проекту

## Цель

Готовить статусную отчетность по проекту. Главный агент выбирает skill «Статусная отчетность» (jira-status-report), собирает результаты и готовит понятную сводку. Часть работы выполняют субагенты: их выводы использует главный агент — решение об остановке, исправлениях и финальный текст остаются за ним.

## Роли

### Главный агент

- Определяет вводные: проект, период, доски, особенности (раздел 1 SKILL.md, реестр project-rules.md).
- Собирает данные из Jira и считает показатели (разделы 2–6 SKILL.md).
- Готовит понятную сводку для заказчика (раздел 7 SKILL.md).
- Координирует субагентов. Субагенты не общаются с пользователем — всю коммуникацию ведет главный агент.

### Субагент «Проверяющий данных»

Запускает проверку собранных данных и возвращает только список найденных проблем — без исправлений и без текста отчета.

Проверяет:

- Дубли: задача посчитана в двух показателях одновременно (например, «закрыто» и «передано в prod-тестирование»); повторения ключей при постраничной выгрузке; одна задача в нескольких группировках отчета.
- Пропуски: обрыв пагинации (страница ровно по лимиту — запросить следующую); задачи, выпавшие из-за слишком узкого фильтра; пустые обязательные поля (статус, даты); выборки, неполные относительно разделов отчета (для какого-то раздела нет данных).
- Неверные даты: даты вне окна периода; граница периода применена с ошибкой (включение/исключение последнего дня); due date в прошлом у задач, учтенных как плановые; смешение даты изменения и даты завершения; некорректный формат или таймзона.

### Субагент «Аналитик»

Сравнивает уже посчитанные показатели текущего и предыдущего периодов (две недели, два отчета) и объясняет заметные изменения.

Ограничения:

- Работает только с готовыми числами и подтвержденными фактами (комментарии, переходы статусов, изменения дат в Jira, предыдущие отчеты).
- Причину изменения называет только при подтверждении данными. Нет подтверждения — фиксирует «изменение заметно, причина данными не подтверждается» и ничего не придумывает.

### Субагент «Проверяющий отчёта»

Сверяет готовый отчет с источниками и возвращает только список расхождений:

- каждое число отчета ↔ соответствующая JQL-выборка;
- границы периода и рабочие дни ↔ вывод scripts/working_days.py;
- категории и формулировки рисков ↔ references/risks.md;
- служебная информация ↔ фактический отбор задач (доски, лейблы, критерий завершенности);
- разделы «Изменения по срокам» и «Нужно от заказчика» существуют только при наличии фактов.

## Данные и доступ

- Использовать только данные за запрошенный период: выборки Jira в окне периода; при файловой выгрузке — только обезличенную выгрузку за запрошенный период.
- Не открывать файлы .env, пароли и персональные данные клиентов.
- Не изменять исходные данные: задачи Jira — только чтение (никаких правок, комментариев, переходов по статусам), файлы выгрузок не редактировать.
- В клиентский отчет персональные данные не включать; имена сотрудников упоминать только там, где это необходимо для смысла (служебная информация, причина блокировки).

## Порядок работы

1. Уточни проект, период отчёта, доски и особенности (раздел 1 SKILL.md; проект в реестре — спросить только недостающее, проекта в реестре нет — все четыре вводных).
2. Собери все данные по требованиям (раздел 2 SKILL.md + проектные правила отбора из реестра).
3. Запусти проверку данных (субагент «Проверяющий данных»).
4. При ошибках данных остановись и перечисли их пользователю. Отчет не готовить, пока проблемы не устранены; исправление — перезапрос или уточнение данных, а не правки «на глаз».
5. Подготовь отчет (разделы 5–7 SKILL.md). Есть данные за предыдущий период — сравнение показателей выполняет субагент «Аналитик».

## Перед завершением

- Сверь итоговые результаты с параметрами скрипта: субагент «Проверяющий отчёта» сопоставляет числа отчета с выводом scripts/working_days.py (границы периода, рабочие дни) и с результатами JQL-выборок; расхождения устраняются до выдачи.
- Пройди чек-лист references/quality-checklist.md.
- Показатель, который невозможно достоверно подтвердить, не придумывать; отчет должен отправляться заказчику без редактирования.
