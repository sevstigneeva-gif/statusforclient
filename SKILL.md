# Клиентский статус-отчет по Jira

Регулярный статус для заказчика за отчетный период, готовый к копированию и отправке без правок. Главная единица анализа — изменение, результат или значимое состояние задачи, а не Jira-задача сама по себе. Отчет показывает динамику: что произошло, какие результаты получены, что продолжается, какие риски и планы.

Работа организована по схеме «главный агент + субагенты»: главный агент собирает результаты и готовит сводку, субагенты проверяют данные, сравнивают периоды и сверяют отчет со скриптом. Роли, границы доступа и порядок работы — [AGENTS.md](AGENTS.md).

## 1. Входные данные

Перед формированием отчета должны быть определены четыре базовых вводных. Ответ, который не дает запрос и реестр проектных правил, — запросить у пользователя до сбора данных:

1. Для какого проекта отчет? Проект неоднозначен (несколько похожих, неясная область) — уточнить. Несколько проектов — анализировать каждый независимо (см. изоляцию ниже), в отчете оформить отдельными блоками.
2. За какой период? Даты начала и окончания и ритм (спринт, месяц, произвольный диапазон). Период не указан — взять из контекста запроса (например, «за сентябрь», «с прошлого статуса»); если определить невозможно — запросить у пользователя.
3. По каким доскам? Весь проект (стандартный набор досок features и requirements) или только разработка (доска features). Доска management в отчете не участвует. Если наименования досок на проекте отличаются от стандартных — уточнить у пользователя, какие доски включать в отчет.
4. Есть ли особенности, которые надо учитывать? Отбор задач, критерий завершенности, терминология, обращение к заказчику в отчете, календарь, прочее.

- Проектные правила: у отдельных проектов есть индивидуальные правила отчета. Перед формированием отчета найти проект в реестре [references/project-rules.md] и применить его правила; правила одного проекта не действуют на другие проекты. Проект есть в реестре — известные ответы на четыре вопроса брать из реестра и запроса, спрашивать только недостающее (как правило, период). Проекта в реестре нет — задать все четыре вопроса полностью, до начала сбора данных; без ответов работать по умолчанию (все задачи по выбранному набору досок, завершенность = закрытие задачи) и пометить допущения в служебной информации. Полученные ответы зафиксировать в реестре project-rules.md. Пользователь сообщил новые правила проекта в диалоге — дописать их в реестр.

## 2. Сбор данных из Jira

Использовать Jira-инструменты, доступные в окружении (типично — MCP-инструменты: поиск задач по JQL, чтение задачи с полями и changelog, комментарии; при их отсутствии — попросить у пользователя выгрузку).

По каждой релевантной задаче собрать: ключ, проект, описание, статус, даты создания/изменения/завершения, due date, deadline, remaining estimate, исполнителя, комментарии за период, labels/components, epic/parent, связи и блокирующие связи, флаги/blocker, релизы, следы согласований и решений заказчика.

Практика выборки:
- Задачи собирать по запрошенному набору досок проекта (features, requirements — см. входные данные); задачи с доски management в отчет не включать.
- Проектные правила отбора из реестра (references/project-rules.md — например, отбор по лейблам на Petstory) применять ко всем выборкам: изменения за период, завершенные, просроченные, запланированные, заблокированные. Служебная статистика считается по отфильтрованному набору.
- Задачи периода: JQL по проекту с условием на изменение или создание в отчетном периоде (например, `project = X AND updated >= <start> AND updated < <end+1d>`).
- Для плана следующего периода дополнительно: открытые задачи с датами в следующем периоде и подтвержденные к продолжению задачи In Progress.
- Deadline и due date — разные сущности, не смешивать. Deadline часто лежит в отдельном custom field — выяснить поля конкретного инстанса по образцу задач, а не предполагать.

Не использовать данные, которых нет в Jira или в доступных предыдущих отчетах. Ничего не придумывать.

Проверка данных — обязательный шаг после сбора: субагент «Проверяющий данных» (см. AGENTS.md) проверяет дубли, пропуски и неверные даты и возвращает только список найденных проблем. Найдены ошибки — остановиться, перечислить их пользователю и не готовить отчет, пока данные не исправлены; исправление — перезапрос или уточнение данных, а не правки «на глаз».

## 3. Изоляция проектов (жесткое правило)

Контекст, история отчетов и анализ строго разделены по проектам. Для проекта используются только его задачи, статусы, сроки, estimate, зависимости, предыдущие отчеты и зафиксированные в его контексте планы и риски.

Запрещено переносить между проектами результаты, риски, сроки, планы и интерпретацию задач — даже если у проектов общий заказчик, команда, продукт, компоненты или тематика.

Межпроектная связь учитывается только как внешняя зависимость, явно зафиксированная в Jira: риск относится к проекту зависимой задачи, задача другого проекта упоминается как внешняя (например, «срок реализации WEB-123 зависит от завершения API-456 в другом проекте»), самостоятельных выводов о состоянии чужого проекта делать нельзя.

## 4. Предыдущие отчеты

Источники: приложенные пользователем файлы, сохраненные копии в рабочей папке, Confluence (если доступен). Для задачи проекта A — только отчеты проекта A; если отчетов по проекту нет, не восполнять контекст отчетами других проектов.

Зачем: видеть историю и переходы задач, не представлять продолжающуюся задачу как новую («продолжили и передали на тестирование», а не «начали разработку»), находить незавершенные планы прошлого периода, отслеживать накопление рисков.

Приоритет: предыдущие отчеты дают контекст и динамику, но не заменяют актуальные данные Jira. При противоречии — приоритет у Jira. Старые формулировки, сроки и риски не переносить автоматически, если они больше не подтверждаются.

Сравнение уже посчитанных показателей текущего и предыдущего периодов выполняет субагент «Аналитик» (см. AGENTS.md): объясняет заметные изменения, опираясь только на подтвержденные данными факты; причины без подтверждения не придумывает.

## 5. Анализ периода

Для каждой задачи определить, что произошло за период: изменение статуса, новый результат, продолжение работы, блокировка, изменение сроков, существенное содержание комментариев.

- Результат — не только «Done». Значимы: передача на тестирование, публикация, согласование требований, принятые решения, проведенное обследование/анализ/встреча, изученные материалы, подготовленные варианты и концепции, промежуточные результаты аналитики и дизайна. Предпроектные работы не обесценивать как «активность без результата».
- Не считать факт существования задачи результатом автоматически: оценивать, имеет ли задача самостоятельное значение для текущего статуса проекта.
- Связанные задачи (одна функциональность, сценарий, доработка, этап, направление, проблема) группировать в один пункт с ключами в скобках: «Доработали форму авторизации: исправили валидацию, маску телефона и обработку ошибок (WEB-123, WEB-125, WEB-127)». При группировке не терять существенные результаты отдельных задач. Количество пунктов не ограничивать искусственно и не раздувать незначительными задачами.
- Отделять факт от плана: «завершили/передали/согласовали» — в результаты; «завершить/передать/подготовить» — в план. Не смешивать в одном пункте.
- Технический шум не включать в клиентский отчет: мелкие технические и служебные задачи, подзадачи, чей результат отражен в родительской, обсуждения без результата, незначительные исправления. Исключение: задача значима для результата, срока, проблемы или риска — тогда включить или использовать как основание вывода.

## 6. Риски

Прочитай [references/risks.md](references/risks.md) перед оценкой. Опорные правила:

- Категории: 🔴 проблема (срок уже нарушен или явная блокировка), 🔴 высокий риск (remaining estimate больше доступных рабочих дней до срока), 🟡 риск (remaining estimate равен доступным рабочим дням — нет запаса), 🟡 явный риск (зафиксирован в Jira).
- Рабочие дни считать скриптом [scripts/working_days.py](scripts/working_days.py), календарь проекта приоритетнее пн–пт, праздники исключать только при наличии календаря.
- In Progress сам по себе не риск. Нет estimate или срока — никаких предположений о риске.
- Одна причина — один риск со списком всех зависимых задач; не дублировать по каждой задаче.

## 7. Отчет

Прочитай [references/report-format.md](references/report-format.md): служебная информация для РП (отдельно по каждому проекту), структура клиентского статуса (результаты, проблемы и риски, изменения по срокам, следующий период, нужно от заказчика), правила каждого раздела, стиль и полный шаблон. Опорные запреты:

- Бюджет из estimate не оценивать: никаких переводов story points/часов/дней в деньги и выводов о перерасходе. Нет финансовых данных — раздела «Бюджет» нет.
- Изменения по срокам и запросы к заказчику выводить только при наличии фактических данных, иначе раздел не выводить.

## 8. Перед выдачей

Субагент «Проверяющий отчёта» (см. AGENTS.md) сверяет все с выводом скрипта: каждое число отчета — с результатами JQL-выборок, границы периода и рабочие дни — с выводом [scripts/working_days.py](scripts/working_days.py). Возвращает список расхождений; расхождения устраняются до выдачи.

Пройди чек-лист [references/quality-checklist.md](references/quality-checklist.md). Показатель, который невозможно достоверно определить, не придумывать. Отчет должен отправляться заказчику сразу, без редактирования.
